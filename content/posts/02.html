When our professor explained the backpropagation algorithm during a deep learning course, he walked us through the manual derivation of the gradients for a simple fully connected model with one hidden layer. It quickly became clear to me that that this approach was unfeasible for more complex and larger model architectures (not to mention it being extremely tedious and error-prone). A bit later in the course, during our lab sessions with PyTorch, I discovered that in practice you can simply call the backward() method, and the framework takes care of computing all the gradients for you, no matter how complicated the network architecture is. At first, it honestly felt like magic, so I immediately started digging deeper to understand how these frameworks were able to pull this off. This post is my personal attempt to explain the algorithm that makes that magic possible: reverse-mode automatic differentiation.

Finite Difference

Many scientific problems require some form of derivative computation. Naturally, having an efficient and automatic way to compute derivatives on a computer is extremely important. Let's assume for example that we have a simple function \(f(x) = 2 \sin(x^3)^2\) for which we want to compute its derivative. In a computer program we would represent this function straightforwardly like this: {% call code("python") %} def f(x: float) -> float: return 2 * math.sin(x**3)**2 {% endcall %} A naive approach to compute its derivative would be to directly apply the classical definition of a derivative (the one many of you probably remember from high school calculus). \[ f'(x) = \lim_{h \to 0} \frac{f(x + h) - f(x)}{h} \] Of course we can't implement limits with quantities that goes to zero in the computer due to the finite precision of floating point numbers, but the idea that we can get from this formula is that the derivative value will become closer to the actual value as the value of \(h\) becomes closer to \(0\). In this way, we can actually get an approximation of the real value of the derivative with this simple implementation. {% call code("python") %} def df(x: float) -> float: h = e-10 return (f(x) - f(x + h)) / h {% endcall %} It should not come as a surprise that this technique is called finite difference, since it relies on a small but finite increment \(h\) instead of an infinitesimal differential (in the abstract mathematical sense). The main drawback of this approach is that, due to the finite precision of floating point arithmetic, we may encounter catastrophic cancellation when \(h\) is chosen too small (on the order of machine \(\epsilon\)), whereas if \(h\) is not small enough, the approximation becomes inaccurate.

Symbolical Derivation

To solve this problem, one may think: why not just derive symbolically and then evaluate the symbolical derivative at a specific point? In this way, one should be able to have the exact value (up to machine precision) of the derivative, without the numerical problems tat plagues the finite difference method. The main downside of this approach can be explained with a simple example. Consider the following function \(g(x) = (x+1)(x+2)(x+3)\), if we derive it symbolically we get: \[ g'(x) = (x+2)(x+3) + (x+1)(x+3) + (x+1)(x+2) \] It is obvious that the number of terms in the expression is growing in a combinatorial way. This is a common example of a phenomenon called "expression swell", where the size of the derivative expression explodes in size with respect to the size of the expression of the original function. This problem may cause extremely long expression for relatively complex function that cannot even fit in memory.

Automatic Differentiation

To explain the method that solves the problems that plagues both of these approaches we should start from a simple yet powerful concept in math: the chain rule. \[ f'(g(x)) = f'(g(x)) \cdot g'(x) \] (In practice, this formula is more oftern written in partial notation). \[ \frac{\partial f(g(x))}{\partial x} = \frac{\partial f(g(x))}{\partial g(x)}\frac{\partial g(x)}{\partial x} \] Intuitively, this formula tells us that the rate of change of a composite function is the rate of change of the outer function multiplied by the rate of change of the inner function. We can use this main idea to build our algorithm. The idea is rather simple: since any function of arbitrary complexity can be seen as a composite function of more elementary function, we can recursively split our function into progressively elementary functions and then simply apply the chain rule. For example, if we consider the function from the example above, we can decompose it into these intermediate values. \[ z = 2u^2 \quad u = sin(v) \quad n = x^2 \] Then we can simply apply the chain rule. \[ \frac{\partial z}{\partial x} = \frac{\partial z}{\partial u} \frac{\partial u}{\partial n} \frac{\partial n}{\partial x} \] If we look closely, we can compute these partial derivatives from two different starting point. If we start from the rightmost term, we can compute that derivative right away, because the only input whose $n$ depends on is \(x\), which is the input of the whole function itself. We can then propagate the previous gradients to the subsequent computations

Forward Mode

If we start the computation from the first intermediate value (which in our example is \(v\)), we obtain the first flavour of automatic differentiation, which is the forward accumulation mode. To do that, we basically derive each intermediate variable \(v_i\) with respect to the input of the entire expression \(\dot{v_i} = \frac{\partial v_i}{\partial x}\). To do that, we can re-use the previously discussed chain rule. \[ \begin{split} \dot{n} = \frac{\partial n}{\partial x} = \frac{\partial n}{\partial x}\frac{\partial x}{\partial x}\\[.5em] \dot{u} = \frac{\partial u}{\partial x} = \frac{\partial u}{\partial n}\frac{\partial n}{\partial x}\\[.5em] \dot{z} = \frac{\partial z}{\partial x} = \frac{}{} \end{split} \]
